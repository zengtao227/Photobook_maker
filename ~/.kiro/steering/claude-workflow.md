# Claude 全局工作流程规范

本文件定义 Claude Code 在所有项目中的强制工作流程。

---

## 🚨 强制第一性原理分析框架

**在提出任何修改方案之前，必须显式输出以下分析（不可跳过）：**

### 📋 必须输出的分析框架

每次提出方案前，必须在回复中包含以下结构化分析：

```
## 第一性原理分析

### 1. 问题本质
- 这个问题的根本原因是什么？（不是表面症状）
- 为什么会出现这个问题？

### 2. 现有机制审查
- 系统中是否已有相关机制可以复用？
- 如果有，为什么不能直接使用？

### 3. 约束条件
- 硬约束：[不可违反的规则]
- 软约束：[可调整的参数]

### 4. 方案评估
- 方案A: [描述] - 优点/缺点
- 方案B: [描述] - 优点/缺点（如果有）
- 推荐方案及理由

### 5. 最小化检查
- 这个方案是否是最简单的？
- 能否用更少的代码实现？
- 是否在添加代码？如果是，有没有办法通过删除或修改现有代码来解决？

### 6. 副作用检查
- 这个修改会影响哪些其他模块？
- 是否会引入新的问题？
```

**Remember**: 最好的代码是没有代码，次好的是更少的代码

## 🔍 修复后全面检查规范（强制）

**修复任何问题后，必须对整个代码库进行相似问题的全面检查！**

### 检查流程

```
1. 修复一个具体问题
2. 分析问题的本质模式（如：属性未初始化、变量拼写错误、缺少导入等）
3. 在整个代码库中搜索相似模式
4. 修复所有发现的相似问题
5. 运行代码检查验证
```

### 常见需要全面检查的问题类型

| 问题类型 | 检查方法 | 示例 |
|----------|----------|------|
| 属性未初始化 | 对比 `self.xxx` 使用 vs `__init__` 定义 | `self.current_mid_price` 被使用但未定义 |
| 变量拼写错误 | grep 搜索相似变量名 | `curent_price` vs `current_price` |
| 缺少导入 | 检查所有使用的类/函数是否已导入 | 使用 `OrderedDict` 但未导入 |
| 类型不匹配 | 检查函数参数和返回值类型 | 期望 `float` 但传入 `str` |
| 异步/同步混用 | 检查 `await` 是否正确使用 | 调用 async 函数忘记 `await` |
| 边界条件遗漏 | 检查所有相似逻辑的边界处理 | 某处检查了 `None`，其他地方未检查 |

### 检查命令示例

```bash
# 检查所有 self.xxx 属性使用
grep -oE 'self\.[a-zA-Z_][a-zA-Z0-9_]*' file.py | sort -u

# 对比已定义的属性（在 __init__ 或类中赋值的）
grep -E 'self\.[a-zA-Z_][a-zA-Z0-9_]*\s*=' file.py | grep -oE 'self\.[a-zA-Z_][a-zA-Z0-9_]*' | sort -u

# 搜索相似模式
grep -rn "pattern" --include="*.py" .
```

### 输出格式

修复后必须在回复中包含：

```
## 相似问题检查

### 检查范围
- [检查了哪些文件/模块]

### 检查结果
- ✅ 未发现其他相似问题
- 或
- ⚠️ 发现 N 个相似问题，已修复：
1. [问题描述 + 修复位置]
2. ...
```

## 🔧 代码质量检查（强制）

**修改代码后，必须运行代码检查验证！**

### 检查优先级

1. **项目专用脚本**（如 `./check_code.sh`）
   - 优先使用

2. **通用检查命令**（如果项目无专用脚本）：

```bash
# Python 语法检查
python -m py_compile *.py

# Ruff 检查（如果安装）
ruff check .

# MyPy 类型检查（如果安装）
mypy .
```

### 检查内容

- ❌ 语法错误
- ❌ 未定义变量（拼写错误、缺少导入）
- ❌ 类型错误
- ❌ 代码风格问题

**DO NOT** 在没有运行代码检查的情况下标记任务完成！

---

## ⚠️ 触发条件

以下情况**必须**输出第一性原理分析框架：

1. 用户要求修复bug或添加功能
2. 用户要求优化或重构代码
3. 对比分析后提出改进建议
4. 任何涉及代码修改的场景

---

## ❌ 禁止行为

- ❌ 跳过分析直接给出代码方案
- ❌ 只给出一个方案而不考虑替代方案
- ❌ 不检查现有机制就添加新代码
- ❌ 修改代码后不运行代码检查
- ❌ 基于猜测修改代码
- ❌ 添加"以防万一"的复杂逻辑
- ❌ **修复一个问题后不检查是否存在相似问题**

---

## ✅ 正确工作流程

```
1. 收到修改请求
2. 阅读并理解相关代码
3. 输出「第一性原理分析」框架（必须）
4. 等待用户确认方案
5. 实施代码修改
6. 【重要】全面检查相似问题
7. 运行代码检查验证
8. 确认无误后提交并推送到远端（如果用户要求）
9. 完成
```

## 📝 Git 提交规范

代码修改完成并通过检查后，提交并推送到远端：

```bash
# 1. 查看修改
git status
git diff

# 2. 添加修改
git add -A

# 3. 提交（使用有意义的提交信息）
git commit -m "fix/feat/refactor: 简要描述修改内容"

# 4. 推送到远端
git push
```

**提交信息规范**:
- `fix:` 修复bug
- `feat:` 新功能
- `refactor:` 重构代码
- `docs:` 文档更新
- `style:` 代码格式调整（不影响逻辑）
- `perf:` 性能优化
